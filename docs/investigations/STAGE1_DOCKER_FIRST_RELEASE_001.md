# Stage-1 Docker-first release boundary

Baseline: `c3925a977d23b4eb2343a3d5206bf7dff52d0f42`

## Root cause

The full workspace test in the former Stage-1 host job pulled the native node
dependency chain below. The core job intentionally has no host LLVM/libclang,
so `clang-sys` failed while probing `llvm-config` and `libclang.so`.

```text
CLANG_SYS_DEPENDENCY_PATH

clang-sys v1.8.1
└── bindgen v0.72.1
    └── librocksdb-sys v0.17.3+10.4.2 (build dependency)
        └── rocksdb v0.24.0
            └── kvdb-rocksdb v0.21.0
                ├── sc-client-db v0.52.0
                │   ├── sc-cli → minijam-node
                │   ├── sc-consensus-grandpa → minijam-node
                │   └── sc-service → minijam-node
                └── sp-database v10.0.1
                    ├── sc-client-api → minijam-node
                    ├── sc-client-db → minijam-node
                    └── sp-blockchain → minijam-node
```

The owning workspace package is `minijam-node`. Stage-1 Core therefore uses
the explicit positive package list in `scripts/stage1-core-packages.sh` and
guards that graph with `scripts/check-stage1-core-dependencies.sh`.

## Ownership

`.github/workflows/ci.yml` validates the LLVM-free core source surface. The
Stage-1 Docker image job and release workflow own compilation and tests for the
three native production roles. `deploy/stage1/Dockerfile` installs native
build dependencies only in its builder stage and copies only the resulting
role binary into each non-root runtime target.

Stage-1 release images are the authoritative payloads:

- `ghcr.io/archelabs/minijam-node`
- `ghcr.io/archelabs/minijam-worker`
- `ghcr.io/archelabs/minijam-formal-rpc`

Chain specs are generated by executing the exact candidate node image. The
same image references are then used for compact smoke, restart smoke, and
published-digest smoke. The Service Toolchain workflow, Service 0 artifacts,
and pinned Jambda revision remain separately owned.
